## 1. Objective

Investigate how Docker exposes services running inside isolated containers through host ports.

Compare direct container-IP communication with Docker port publishing, and inspect the mechanisms used to forward incoming connections.

**Success Criteria**
- Run an HTTP server inside a Docker container.
- Access the server through a published host port.
- Inspect Docker's port-binding configuration.
- Identify Docker's userland proxy and NAT rules.

## 2. Network Topology

```text
Linux Host
│
├── 127.0.0.1:18080
│         │
│    Docker Port Publishing
│         │
├── docker0 (172.17.0.1/16)
│         │
│      veth pair
│         │
└── netlab-http
       172.17.0.2:80
           │
       HTTP Server
```

The HTTP server listens on TCP port 80 inside the container. Docker publishes this service through TCP port 18080 on the host.

The port is bound to the host's loopback address to avoid intentionally exposing the test service to external networks.

## 3. Experiment

### 3.1 Initial HTTP Server Deployment

The first attempt used Alpine Linux and BusyBox's HTTP server.

```bash
sudo docker run -d \
  --name netlab-http \
  --network bridge \
  -p 127.0.0.1:18080:80 \
  alpine:3.22 \
  sh -c 'mkdir -p /www && echo "Hello from Docker!" > /www/index.html && exec httpd -f -p 80 -h /www'
```

**Observed result:**

```text
httpd: not found
```

The container was created but its main process failed because the `httpd` executable was unavailable.

A subsequent HTTP request failed:

```text
curl: (7) Failed to connect to 127.0.0.1 port 18080
```

**Analysis**

Successful container creation does not guarantee that the container's application is running.

Before investigating network connectivity, the container's process state and application logs should be checked.

### 3.2 Recreate the HTTP Container

The failed container was replaced with a Python-based HTTP server.

```bash
sudo docker rm netlab-http

sudo docker run -d \
  --name netlab-http \
  --network bridge \
  -p 127.0.0.1:18080:80 \
  python:3.13-alpine \
  python -m http.server 80 --bind 0.0.0.0
```

The Python HTTP server listens on all IPv4 addresses within the container's network namespace.

Inspect the container:

```bash
sudo docker ps --filter name=netlab-http
sudo docker port netlab-http
```

**Observed port binding:**

```text
80/tcp -> 127.0.0.1:18080
```

The container remained in the running state.

### 3.3 Verify HTTP Connectivity

```bash
curl -v http://127.0.0.1:18080/
```

**Observed result:**

```text
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.13.18
Content-Type: text/html; charset=utf-8
```

The response body contained a directory listing generated by Python's HTTP server.

**Analysis**

The HTTP request reached the application running inside the container.

Docker successfully exposed container port 80 through host port 18080.

### 3.4 Inspect the Docker Userland Proxy

```bash
sudo ss -lntp '( sport = :18080 )'
```

**Observed output:**

```text
LISTEN ... 127.0.0.1:18080 ...
users:(("docker-proxy",pid=394088,fd=7))
```

This confirmed that a `docker-proxy` process was listening on the published host port.

### 3.5 Inspect Docker NAT Rules

```bash
sudo iptables -t nat -S DOCKER
```

**Observed rule:**

```text
-A DOCKER -d 127.0.0.1/32 ! -i docker0 -p tcp -m tcp --dport 18080 -j DNAT --to-destination 172.17.0.2:80
```

This rule configures Destination NAT for matching TCP traffic.

| Packet field | Before DNAT | After DNAT |
|---|---|---|
| Destination IP | 127.0.0.1 | 172.17.0.2 |
| Destination port | 18080 | 80 |

The rule matches traffic destined for `127.0.0.1:18080` that does not enter through `docker0`.

**Important:** The presence of both a `docker-proxy` listener and a DNAT rule does not establish which mechanism processed the specific localhost request. That would require additional tracing.

## 4. Analysis

### Port Publishing

Docker uses the following format:

```text
HOST_IP:HOST_PORT:CONTAINER_PORT
```

For this experiment:

```text
127.0.0.1:18080:80
```

- Host IP: `127.0.0.1`
- Host port: `18080`
- Container port: `80`

The application's listening port remains unchanged inside the container.

### Direct Routing vs. Published Ports

Two paths can reach the same container service.

**Path A — Published port**

```text
127.0.0.1:18080
       |
Docker port publishing
       |
172.17.0.2:80
```

**Path B — Direct container IP**

```text
172.17.0.2:80
       |
Linux routing
       |
Container HTTP Server
```

Path B does not require destination address translation because the client already specifies the container's IP address and listening port.

Direct container-IP access was discussed but not independently confirmed through a successful curl capture in this experiment.

### Userland Proxy vs. DNAT

Docker can use kernel NAT rules and a userland proxy to support published ports.

This experiment confirmed that both mechanisms were configured.

Further packet tracing would be required to establish the exact processing path for different connection sources.

## 5. Conclusion

Successfully deployed an HTTP server inside Docker and accessed it through a published host port.

**Verified Findings**
1. Docker port publishing maps a host endpoint to a container endpoint.
2. The host and container ports do not need to match.
3. The HTTP server returned `200 OK` through the published port.
4. Docker created a userland proxy listener.
5. Docker installed a DNAT rule targeting the container.
6. An application startup failure can initially appear to be a network connection failure.

**Key Finding:** Docker port publishing makes an isolated container service accessible through a host address and port, using networking mechanisms such as NAT and userland proxying.

## 6. Further Investigation

## 7. Troubleshooting Note

The initial failure was caused by a missing executable rather than a networking problem.

This experiment reinforced the importance of separating application-level failures from network-level failures during troubleshooting.
