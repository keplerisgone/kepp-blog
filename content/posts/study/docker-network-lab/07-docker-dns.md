## 1. Objective

Investigate the differences between Docker's default bridge and a user-defined bridge network.

Verify Docker's embedded DNS service and examine how containers can connect to multiple networks simultaneously.

**Success Criteria**
- Demonstrate that IP communication works on the default bridge.
- Reproduce the failure of container-name resolution.
- Create a user-defined Docker network.
- Resolve container names using Docker's embedded DNS.
- Observe multiple network interfaces inside a container.

## 2. Network Topology

Two existing containers were initially connected to Docker's default bridge.

A new user-defined bridge network, `lab-net`, was created and connected to both containers.

```text
                  Linux Host
              ┌────────┴────────┐
              │                 │
           docker0           lab-net
        172.17.0.1         172.18.0.1
              │                 │
              │                 │
         veth pairs        veth pairs
              │                 │
        ┌─────┴─────────────────┴─────┐
        │                             │
     netlab-a                      netlab-b
        │                             │
   172.17.0.2                    172.17.0.3
   172.18.0.2                    172.18.0.3
```

Each container has an interface on each network.

The second subnet was assigned automatically by Docker.

## 3. Experiment

### 3.1 Test Name Resolution on the Default Bridge

```bash
sudo docker exec netlab-a ping -c 3 netlab-b
```

**Observed result**

```text
ping: bad address 'netlab-b'
```

Next, test communication using the container's IP address:

```bash
sudo docker exec netlab-a ping -c 3 172.17.0.3
```

**Observed result**

```text
3 packets transmitted
3 packets received
0% packet loss
```

**Analysis**

IP connectivity worked, but container-name resolution failed.

The default Docker bridge does not ordinarily provide automatic container-name resolution.

This experiment demonstrates that DNS resolution and IP connectivity are distinct mechanisms.

### 3.2 Create a User-defined Bridge Network

```bash
sudo docker network create lab-net
sudo docker network inspect lab-net
```

Docker created a new network using the bridge driver.

The observed container addresses later confirmed that `lab-net` used the `172.18.0.0/16` subnet.

### 3.3 Connect Existing Containers

```bash
sudo docker network connect lab-net netlab-a
sudo docker network connect lab-net netlab-b
```

The containers remained attached to the original default bridge while also joining the new network.

This produced a multi-homed network configuration.

### 3.4 Inspect Docker DNS

```bash
sudo docker exec netlab-a cat /etc/resolv.conf
```

**Observed output (relevant fields)**

```text
# Generated by Docker Engine.
nameserver 127.0.0.11
search tal aa3c13.ts.net
options ndots:0
```

The search domain in the actual output was associated with the host's Tailscale configuration.

The important result was:

```text
nameserver 127.0.0.11
```

This is Docker's embedded DNS resolver, accessible from the container's networking environment.

The resolver provides name resolution for containers on user-defined Docker networks.

### 3.5 Verify Container Name Resolution

```bash
sudo docker exec netlab-a ping -c 3 netlab-b
```

**Observed result**

```text
PING netlab-b (172.18.0.3)

3 packets transmitted
3 packets received
0% packet loss
```

**Analysis**

The container name `netlab-b` successfully resolved to `172.18.0.3`, its address on the shared user-defined network.

This is direct evidence that Docker's embedded DNS provides container-name resolution.

### 3.6 Inspect Network Interfaces

Attempted commands:

```bash
sudo docker exec netlab-a ip -br addr
sudo docker exec netlab-b ip -br addr
```

**Observation**

Both commands displayed the BusyBox `ip` usage message.

The Alpine container used BusyBox utilities, whose `ip` implementation did not support the `-br` option.

The recommended alternative was:

```bash
sudo docker exec netlab-a ip addr
sudo docker exec netlab-b ip addr
```

The successful name-based ping and Docker network configuration established that both containers were connected to the user-defined network.

The complete interface listing was not captured in this experiment.

## 4. Analysis

### Default Bridge vs. User-defined Bridge

| Feature | Default bridge | User-defined bridge |
|---|---|---|
| Linux Bridge | docker0 | Separate bridge |
| Container IP communication | Supported | Supported |
| Automatic name resolution | Not normally supported | Supported |
| Docker embedded DNS | Not normally provided | 127.0.0.11 |
| Network management | Shared default network | Explicit network membership |

### DNS Resolution vs. Network Connectivity

DNS converts a hostname into an IP address.

IP connectivity allows packets to reach the resolved destination.

The initial name-based ping failed even though communication by IP address succeeded.

After joining `lab-net`, name resolution succeeded and the container could communicate using `netlab-b` instead of its IP address.

### Multi-homing

A multi-homed system has interfaces connected to multiple networks.

In this experiment, each container was connected to:
- Default bridge: `172.17.0.0/16`
- User-defined bridge: `172.18.0.0/16`

A container can therefore have multiple IP addresses, each associated with a different network interface.

However, this does not automatically make the container a router.

Routing between networks requires suitable routing configuration and packet-forwarding capabilities.

## 5. Conclusion

Successfully created a user-defined Docker network and verified automatic container-name resolution.

**Verified Findings**
1. Containers on the default bridge communicated successfully using IP addresses.
2. Container-name resolution initially failed.
3. A user-defined bridge network was created.
4. Both containers were attached to the new network.
5. Docker's embedded DNS resolver appeared at `127.0.0.11`.
6. `netlab-b` resolved to `172.18.0.3` and responded successfully to ICMP.

**Key Finding:** Docker user-defined bridge networks provide automatic container-name resolution, making container communication easier without requiring applications to know fixed container IP addresses.
