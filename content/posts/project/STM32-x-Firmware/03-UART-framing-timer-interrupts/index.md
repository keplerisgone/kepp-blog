## 1. Introduction

In the previous experiments, I implemented UART polling transmission and interrupt-driven reception using STM32F407's USART3 peripheral.

The next objectives were to investigate what happens when UART communication parameters do not match and to implement periodic operations using a hardware timer.

This session consisted of three experiments:

1. Observing UART communication with mismatched baud rates.
2. Configuring TIM2 to generate periodic interrupts.
3. Verifying that UART communication and timer-driven LED blinking work simultaneously.

These experiments provide a foundation for understanding interrupt handling and periodic task execution before introducing FreeRTOS.

## 2. UART Baud Rate and Framing

### 2.1 UART Frame Structure

UART is an asynchronous serial communication protocol.

Unlike synchronous protocols, it does not require a shared clock signal between the transmitter and receiver. Instead, both sides must agree on timing and framing parameters.

The configuration used in this experiment was **115200 8N1**.

| Parameter | Value |
|---|---|
| Baud rate | 115200 |
| Data bits | 8 |
| Parity | None |
| Stop bits | 1 |
| Hardware flow control | None |

An 8N1 UART frame consists of one start bit, eight data bits and one stop bit.

```text
Idle   Start    Data bits (LSB first)   Stop
  1      0      D0 D1 D2 D3 D4 D5 D6 D7   1
```

Therefore, transmitting one byte requires ten bits.

At 115200 baud:

\[
T_{\text{bit}} = \frac{1}{115200} \approx 8.68\ \mu s
\]

A complete 8N1 frame requires:

\[
T_{\text{frame}} = 10 \times T_{\text{bit}}
\approx 86.8\ \mu s
\]

These values assume the configured baud rate is accurately generated by the UART peripheral.

### 2.2 Baud-Rate Mismatch Experiment

The STM32 USART3 was configured to operate at 115200 baud.

First, I opened the Linux serial terminal with the matching configuration:

```bash
sudo picocom -b 115200 --flow n /dev/ttyUSB0
```

Then, without changing the STM32 firmware, I reopened the terminal at 9600 baud:

```bash
sudo picocom -b 9600 --flow n /dev/ttyUSB0
```

The baud-rate difference was substantial.

| Device | Baud rate | Approximate bit duration |
|---|---:|---:|
| STM32F407 | 115200 | 8.68 µs |
| PL2303 / PC terminal | 9600 | 104.17 µs |

The PC attempted to interpret the incoming signal using a sampling interval approximately twelve times longer than the STM32's bit duration.

### 2.3 Experimental Results

With the mismatched settings, the terminal displayed corrupted characters instead of meaningful text.

![Picocom sessions at 115200 and 9600 baud](image%20%281%29.png)

*The terminal shows corrupted output at 9600 baud and readable characters after returning to 115200 baud.*

This demonstrated that UART communication requires compatible timing configurations.

After restoring the PC terminal to 115200 baud, I later confirmed that UART echo communication was working again.

However, this experiment did not directly inspect the STM32 USART status registers. Therefore, although corrupted communication was observed, the test did not establish whether the USART framing error flag (`FE`) was asserted.

### 2.4 Understanding Framing Errors

A UART framing error occurs when the receiver fails to detect the expected stop-bit level at the correct sampling point.

A baud-rate mismatch may result in:

- Incorrectly decoded bytes
- Missing or dropped data
- Framing errors
- Receive overruns, depending on traffic and software handling

The exact outcome depends on how the receiver samples the incoming waveform.

This distinction is important because corrupted application data does not automatically prove that the hardware detected a framing error.

## 3. STM32 Hardware Timer Fundamentals

### 3.1 Why Use a Hardware Timer?

Previously, I implemented LED blinking using:

```c
while (1)
{
    HAL_GPIO_TogglePin(GPIOD, GPIO_PIN_12);
    HAL_Delay(500);
}
```

This produces a periodic LED transition but blocks the main loop during the delay.

A hardware timer offers a different mechanism.

The timer peripheral counts clock cycles independently of the CPU instruction stream and can generate an interrupt when its counter reaches a configured limit.

This allows periodic events to occur while the main program performs unrelated work.

### 3.2 TIM2 Architecture

The STM32F407 provides a general-purpose timer peripheral called TIM2.

The following registers are important for timer configuration and interrupt handling:

| Register | Purpose |
|---|---|
| `TIM2_PSC` | Prescaler — divides the timer input clock |
| `TIM2_ARR` | Auto-reload — determines the counting period |
| `TIM2_CNT` | Current counter value |
| `TIM2_DIER` | Interrupt enable control |
| `TIM2_SR` | Timer status flags |

For a timer operating in up-counting mode, the update event frequency is:

\[
f_{\text{update}} =
\frac{f_{\text{TIM2}}}{(PSC+1)(ARR+1)}
\]

The corresponding period is:

\[
T_{\text{update}} =
\frac{(PSC+1)(ARR+1)}{f_{\text{TIM2}}}
\]

TIM2 receives its clock through the APB1 timer clock domain.

The effective timer clock depends on the MCU clock configuration and APB1 prescaler.

### 3.3 Configuring the Timer Period

I configured the following values in STM32CubeMX:

```c
htim2.Init.Prescaler = 15999;
htim2.Init.CounterMode = TIM_COUNTERMODE_UP;
htim2.Init.Period = 499;
```

If the TIM2 input clock is 16 MHz, these settings produce:

\[
f_{\text{counter}} =
\frac{16{,}000{,}000}{15999+1}
= 1000\ \text{Hz}
\]

The timer update frequency becomes:

\[
f_{\text{update}} =
\frac{1000}{499+1}
= 2\ \text{Hz}
\]

Therefore:

\[
T_{\text{update}} = 0.5\ \text{s}
\]

The intended update interval was 500 ms.

The exact timer clock was not independently recorded during the experiment, and the interval was not measured using a logic analyzer or oscilloscope. Therefore, the 500 ms value is a calculated target rather than a measured result.

## 4. Timer Initialization vs. Timer Start

An important distinction emerged while examining the STM32CubeMX-generated code.

The generated function `MX_TIM2_Init()` contained:

```c
htim2.Instance = TIM2;
htim2.Init.Prescaler = 15999;
htim2.Init.CounterMode = TIM_COUNTERMODE_UP;
htim2.Init.Period = 499;
htim2.Init.ClockDivision = TIM_CLOCKDIVISION_DIV1;
htim2.Init.AutoReloadPreload =
    TIM_AUTORELOAD_PRELOAD_DISABLE;

if (HAL_TIM_Base_Init(&htim2) != HAL_OK)
{
    Error_Handler();
}
```

Initially, I wondered whether `HAL_TIM_Base_Init()` was sufficient to start the timer.

However, initialization and starting are separate operations.

| Function | Role |
|---|---|
| `HAL_TIM_Base_Init()` | Configures the timer |
| `HAL_TIM_Base_Start()` | Starts counting without enabling update interrupts |
| `HAL_TIM_Base_Start_IT()` | Starts counting with update interrupts enabled |
| `HAL_TIM_Base_Stop_IT()` | Stops the timer and disables update interrupts |

`HAL_TIM_Base_Init()` configures the peripheral but does not begin normal periodic counting.

Therefore, I added the following after `MX_TIM2_Init()` in the user-code initialization section of `main()`:

```c
if (HAL_TIM_Base_Start_IT(&htim2) != HAL_OK)
{
    Error_Handler();
}
```

This starts the timer and enables update interrupt generation.

The distinction can be summarized as:

```text
MX_TIM2_Init()
       |
       v
HAL_TIM_Base_Init()
       |
       v
TIM2 configured
       |
       v
HAL_TIM_Base_Start_IT()
       |
       v
TIM2 counting + update interrupts
```

## 5. Implementing the Timer Interrupt Callback

### 5.1 TIM2 Interrupt Configuration

In STM32CubeMX, I configured TIM2 with:

- Internal clock source
- Up-counting mode
- Prescaler: 15999
- Counter period: 499
- TIM2 global interrupt enabled through NVIC

The generated interrupt handler invokes the HAL timer handler:

```c
void TIM2_IRQHandler(void)
{
    HAL_TIM_IRQHandler(&htim2);
}
```

The HAL driver processes the timer interrupt and invokes the relevant application callback.

### 5.2 The Period-Elapsed Callback

I implemented the callback as follows:

```c
void HAL_TIM_PeriodElapsedCallback(
    TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM2)
    {
        HAL_GPIO_TogglePin(
            GPIOD,
            GPIO_PIN_12
        );
    }
}
```

The callback checks the timer instance because the same HAL callback mechanism can be used by multiple timer peripherals.

When TIM2 generates an update event and the interrupt is serviced, the HAL invokes this callback.

The application then toggles PD12, which controls the red channel of the EduBoard's onboard RGB LED.

The callback does not use `HAL_Delay()`.

### 5.3 Complete Interrupt Execution Flow

```text
TIM2 counter increments
          |
          v
Counter reaches update boundary
          |
          v
Timer update event
          |
          v
Update interrupt request
          |
          v
NVIC dispatches TIM2_IRQHandler()
          |
          v
HAL_TIM_IRQHandler(&htim2)
          |
          v
HAL_TIM_PeriodElapsedCallback()
          |
          v
HAL_GPIO_TogglePin(GPIOD, GPIO_PIN_12)
```

This resembles the UART interrupt mechanism implemented previously.

The main difference is the source of the interrupt:

- USART3 generates interrupts in response to communication events.
- TIM2 generates interrupts in response to periodic timer events.

## 7. Simultaneous USART3 and TIM2 Operation

The final experiment was to determine whether UART communication would continue functioning while the hardware timer periodically toggled the LED.

The firmware contained two interrupt-driven components:

```text
                 STM32F407
                      |
           +----------+----------+
           |                     |
         USART3                 TIM2
           |                     |
     RX interrupt         Update interrupt
           |                     |
           v                     v
    UART HAL handler      TIM HAL handler
           |                     |
           v                     v
    UART RX callback      Timer callback
           |                     |
           v                     v
    Main loop echo        Toggle PD12 LED
```

I opened picocom at 115200 baud:

```bash
sudo picocom -b 115200 --flow n /dev/ttyUSB0
```

While the LED continued blinking, I sent characters to the STM32 through the PL2303 adapter.

**Both functions operated successfully at the same time.**

The results confirmed that:

- TIM2 continued producing periodic LED transitions.
- USART3 continued receiving and echoing characters.
- The two features could coexist in the same firmware.

This was a functional test, not a quantitative scheduling or interrupt-latency measurement.

## 8. Concurrency vs. Parallelism

Although the UART and timer functions appeared to run simultaneously, this does not mean that the Cortex-M4 executed both interrupt handlers in parallel.

The STM32F407 contains a single CPU core.

When an interrupt occurs, the processor can temporarily suspend its current execution and run an ISR.

NVIC manages interrupt eligibility, priority, and preemption.

For example:

```text
Main loop
    |
    +-- USART3 interrupt
    |       |
    |       +-- UART receive callback
    |
    +-- TIM2 interrupt
            |
            +-- LED toggle callback
```

The CPU switches between execution contexts as interrupt events occur.

Hardware peripherals such as USART3 and TIM2 can operate concurrently, even while the CPU services their events sequentially or through interrupt preemption.

This distinction will become especially important when working with FreeRTOS tasks.

## 9. Lessons Learned

### 9.1 Communication parameters must match

UART communication depends on compatible baud rates and framing settings.

The 115200-versus-9600 experiment demonstrated the consequences of incompatible timing.

### 9.2 Timer initialization does not start counting

`HAL_TIM_Base_Init()` configures the timer.

`HAL_TIM_Base_Start_IT()` starts the timer and enables update interrupts.

Understanding this separation is essential when configuring STM32 peripherals.

### 9.3 Interrupts allow event-driven firmware

A hardware interrupt allows the CPU to respond to an event without continuously checking a peripheral status register in the application.

This is useful for UART reception, timer updates, external inputs, and sensor events.

### 9.4 Hardware peripherals operate independently

The STM32 can receive UART data and increment a hardware timer counter simultaneously.

The CPU then handles the corresponding software events through the interrupt mechanism.

### 9.5 Functional correctness and timing correctness are different

The LED blink and UART echo were verified.

However, no quantitative measurements were made of:

- Timer update interval accuracy
- Interrupt latency
- Interrupt jitter
- UART throughput under sustained load

These remain future experimental targets.
